# フラッグシップ ローンチチェックリスト

最終更新: 2026-09-29

## 目的

旧アールズスパから店舗名を引き継いだフラッグシップを、Roominkの最初の本番店舗として安全に開始する。

ローンチの入口は次の2つ。

1. 店舗番号 `070-9078-7986` の着信を、Roomink受付番号 `050-3177-0050` へ転送する。
2. 店舗サイト・広告等のWeb予約リンクを、フラッグシップ専用URLへ切り替える。

公開Web予約URL:

`https://app.roomink.net/s/flagship/booking`

## 2026-09-29時点の状態

- クラコール、Twilio、Groundwireを通した `050-3177-0050` の実着信は成功済み。
- フラッグシップ専用Web予約画面は本番へ配置済みで、URLはHTTP 200で表示できる。
- 公開予約APIは現在 `PUBLIC_BOOKING_ENABLED=0` のため、HTTP 503「Web予約は現在準備中です。」を返している。この環境スイッチをローンチ条件として残さず、公開予約を通常状態で利用できる構成へ変更する。
- Web予約の自動テストとローカルでの一連の動作確認は済んでいる。
- 本番の実SMSを使った「認証コード送信 → 予約確定 → 店舗タイムライン反映 → 顧客予約画面確認」の通し試験は未実施。
- 顧客CSV取込機能は本番APIへ配置済み。電話番号一致で既存顧客を更新でき、取込だけではSMSを送らない。

- 2026-09-29の本番マスタ確認では、10月1日以降のシフトはまだ登録されていない。公開予約はシフトから空き枠を作るため、10月分のシフト登録がローンチ前の必須作業である。
- 旧システムの顧客CSVは未受領のため、顧客移行は保留中。

## Web予約の開始方法

店舗別のON/OFFスイッチは設けない。公開予約機能は通常状態で利用可能とし、店舗サイト・広告・SNS等の予約リンクを店舗専用URLへ差し替えた時点を、その店舗のWeb予約開始とする。

現在の `PUBLIC_BOOKING_ENABLED` は、設定漏れで公開予約全体が「準備中」になるため、ローンチ前に依存を外す。環境変数を設定し忘れて予約できない構成を残さない。

店舗専用URLはStoreのslugから店舗を解決する。取得するキャスト、コース、オプション、シフト、顧客、SMS認証情報、確定予約はすべて解決したStoreのIDへ紐付け、他店舗データを混在させない。

`https://app.roomink.net/s/flagship/booking` は公開ページであり、URLを知る人はリンク差し替え前でもアクセスできる。URLを秘密情報やアクセス制御として扱わず、リンク差し替えを一般顧客への案内開始として扱う。

## 顧客情報の移行

顧客情報の取込は電話受付そのものの必須条件ではないが、既存顧客の判別、注意事項、出禁情報を引き継ぐため、原則としてローンチ前に行う。

1. 旧システムから顧客データをCSVで出力してもらう。
2. 元ファイルを変更せず保管し、作業用コピーをRoomink形式へ整える。
3. 名前、電話番号、メール、利用履歴、顧客メモ、運営メモ、注意・出禁情報を対応付ける。
4. Roominkのプレビューだけを実行し、重複・不正電話番号・更新対象を確認する。
5. 取込前に本番DBバックアップを取得する。
6. 承認した行だけを取込む。
7. 件数、代表的な既存顧客、注意・出禁情報を抜き取り確認する。

旧利用履歴は参照用テキストとして保存し、Roominkの予約・売上実績へ混ぜない。顧客データが間に合わない場合でも電話受付は開始できるが、注意・出禁情報を確認できないリスクを店舗と共有する。

## 推奨する公開順序

### 第1段階: 事前準備

1. `PUBLIC_BOOKING_ENABLED` への依存を外し、設定漏れで「準備中」にならないようにする。
2. 本番DBバックアップを取得する。
3. 顧客CSVをプレビュー・取込・確認する。
4. 店舗、ルーム、キャスト、コース、オプション、シフト、注意事項を最終確認する。
5. Groundwireを使用する全受付端末で登録状態と着信許可を確認する。
6. 本番に存在する店舗slug一覧を確認し、各URLがその店舗のIDへ分離されることを確認する。

### 第2段階: Web予約の本番通し試験

1. 外部サイトのリンクはまだ変更せず、フラッグシップ専用URLを直接開く。
2. 管理されたテスト電話番号で1件予約する。
3. SMS認証コードが届くことを確認する。
4. 予約確定後、店舗の予約タイムラインへ1件だけ反映されることを確認する。
5. 顧客の予約確認画面、日時、キャスト、コース、料金、ルーム情報を確認する。
6. 同じ枠への重複予約が拒否されることを確認する。
7. 別店舗のURL・ID・オプションを混在させてもフラッグシップの予約へ入らないことを確認する。
8. テスト予約を識別できる状態で処理し、売上・請求へ混ぜない。

### 第3段階: Web予約URLの切替

1. 店舗サイト、SNS、広告、プロフィール等の現在の予約リンクを洗い出す。
2. 新しいリンクを `https://app.roomink.net/s/flagship/booking` へ変更する。
3. スマートフォンの外部回線からリンクを開き、フラッグシップだけが表示されることを確認する。
4. 旧URLや旧予約サービスへの主要導線が残っていないことを確認する。

Web予約URLは電話転送より先に切り替えられる。ただし、第2段階の本番通し試験が合格してから公開する。

### 第4段階: 電話の切替

1. 店舗と開始時刻を決める。
2. 対象回線とかけ放題適用状況を再確認する。
3. my 楽天モバイルで、`070-9078-7986` から `050-3177-0050` への無条件転送をONにする。
4. 店舗外の登録済み番号から電話し、Groundwireが鳴ることを確認する。
5. 未登録番号から電話し、未登録顧客としてRoominkへ表示されることを確認する。
6. 受付担当が対応開始し、顧客・予約作成まで完了できることを確認する。
7. 不在、拒否、複数着信、アプリ終了時の動作を確認する。

転送をONにした時点で実運用が始まる。端末登録と受付担当の準備が完了する前にONにしない。

### 第5段階: 公開後確認

- 最初の実着信と最初のWeb予約を個別に確認する。
- 当日中は着信、予約、SMS失敗、未対応件数を重点監視する。
- Twilioの通話・SMS利用量とRoominkの集計を照合する。
- 翌営業日に店舗へ、取りこぼし、着信音、通知、画面操作の困りごとを確認する。
- 問題があれば、電話は楽天モバイルの着信転送をOFFにする。Web予約は店舗サイト・広告等のリンクを元へ戻し、新しい一般流入を止める。

## ローンチ判定

### 必須

- Groundwire実着信合格。
- 転送元回線とかけ放題適用の確認。
- 受付端末と担当者の準備完了。
- 公開予約が環境スイッチの設定漏れで停止しない構成になっている。
- フラッグシップURLが店舗ID 35へ解決され、他店舗データと混在しないことを確認済み。
- 本番Web予約の実SMS通し試験合格。
- 予約マスタと公開案内の確認完了。
- ローンチ日以降のシフトが登録され、公開予約枠が表示される。
- ロールバック方法を店舗とRoomink運営が把握。

### 強く推奨

- 既存顧客CSVの取込と抜き取り確認。
- 注意・出禁情報の移行。
- 店舗サイト等の予約リンク一覧作成。
- ローンチ後に確認する担当者と時間帯の確定。

## 利用者側に依頼するもの

- 楽天モバイルの着信転送設定画面とかけ放題加入状況の確認。
- 転送を開始する日時の合意。
- 旧システムの顧客CSV提供。
- 店舗サイト・SNS等の予約リンク変更、または変更権限の共有。
- キャスト、コース、料金、ルーム、案内文の最終確認。

## Roomink側で行うもの

- `PUBLIC_BOOKING_ENABLED` への依存の撤去。
- 店舗slug、店舗ID、予約マスタ、顧客、確定予約の店舗分離確認。
- フラッグシップ公開予約の本番通し試験。
- 顧客CSVの整形、プレビュー、承認後の取込。
- 050着信経路、Groundwire、Roomink通知の最終確認。
- 公開後の通話・SMS・予約監視。
- 問題時のWeb予約停止と切り分け。
