# Work共存対策のローカル開発

この系列はWork専用。通常修正の公開候補は承認済みmainから別に作る。
Workを本番へ公開する許可や、共有ステージングの占有を意味しない。

## ローカル設定

- Python環境はこのツリーの `.venv`、フロント依存はこのツリーの `frontend/node_modules` を使う。
- モバイル依存もこのツリーの `roomink-work/node_modules` に分ける。
- `.env` はGit管理外。ローカルSQLite、ダミーSMS、ダミーメール、Work実電話機能OFFを基本とする。
- 本番・ステージングの `.env` やDBをコピーしない。外部回線の秘密値もローカル基本設定には入れない。
- シェルへexport済みの環境変数は `.env` より優先されるため、接続先・送信設定をローカルへ固定する `work-local` を使う。

```sh
./work-local test core.test_store_schema_coexistence --noinput
```

このテストはDjangoが作成する使い捨てのローカルテストDBだけを使用する。
移行順序の試験内ではテストDBを旧状態へ戻してから前進移行する。
共有DB・既存ローカルDBの巻き戻し操作ではない。

画面をローカルで起動する場合はAPIを8015、フロントを5175など、通常修正とは別ポートにする。
ローカル専用DBを準備した後に、APIは `./work-local runserver 127.0.0.1:8015`、
フロントは `npm run dev -- --host 127.0.0.1 --port 5175` で起動する。
本書の作成だけでサーバーやDB移行を自動実行しない。

モバイルのGit管理外 `.env.local` もローカルAPIを指す。実機の127.0.0.1はMacではないため、
実機接続する際はMacの開発用アドレスを明示してから使う。
EASのpreview等は既存設定で共有ステージングへ接続するため、占有確認なしにビルド・実機試験を開始しない。

## DB共存の変更

適用済みの2つの0093は書き換えず、0094でその末端を合流する。
0095でvoice_receiverへ永続DB既定値groundwireを追加する。
既存行の受信先、資格情報、受信ON/OFFを一括更新しない。

旧Storeモデルからの作成・一括作成・更新、Work/通常双方の出発点からの前進移行、
既存Work選択・資格期限・端末状態の保全、再適用時の変更なしを試験する。
精算側のnomination_fullback_enabledは通常修正系列が所有し、この系列だけで変更しない。
その項目が共有DBに追加された後は、逆方向の互換性と新しい精算方針も確認する。

## 公開前の条件

SQLiteの合格をPostgreSQLや共有ステージングの合格とは扱わない。
PostgreSQL、CI4系統、共有枠の占有、保留・再開手順、固定ステージングの実動作を確認する。
未検証のまま共有DBへ0095を適用したり、通常版へ切り替えたりしない。
本番公開には別途承認が必要。
